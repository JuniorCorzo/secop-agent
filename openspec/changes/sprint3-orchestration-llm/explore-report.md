## 1. Executive Summary

This report maps the technical design and codebase integration points for implementing **Scoring Categorization & Traceability** (ANC-76) and the **LLM Provider Abstraction Layer** (ANC-77). 

We will introduce a database-backed audit trail for scoring (`score_logs`), define a provider-agnostic `LlmProvider` interface, implement the `OpenCodeGoProvider` adapter to connect to our Go-based LLM microservice (running standard OpenAI-compatible endpoints or Ollama local fallbacks), and extend our BullMQ orchestration to handle batch evaluations asynchronously.

## 2. Codebase Discovery & Integration Points

### 2.1 Existing Scoring Module (`apps/nest/src/modules/scoring/`)
* **`HardFiltersService`**: Evaluates hard exclusion filters (financial capacity, residual capacity, UNSPSC code hierarchy, DIVIPOLA geography, excluded contract types/modalities, deadlines).
* **`ScoringEngineService`**: Computes affinity scores between 0 and 100 based on technical, economic, experience, and geographic fits.
* **`MatchingResult` Entity**: Persists the latest match outcome (`status` = `PASSED` | `EXCLUDED`, `score`, `vectorBreakdown`, `justification`).
* **`ScoringWorker`**: Consumes from the `scoring` queue via BullMQ. Currently, it only supports matching a single incoming notice against *all* companies (`scoring-dispatch` job type).

### 2.2 Existing LLM Module (`apps/nest/src/modules/llm/`)
* Currently holds only an empty `LlmModule` placeholder class.
* Environment variables `LLM_BASE_URL` (default: `http://localhost:11434`) and `LLM_API_KEY` are validated in `env.validation.ts` and loaded in `llm.config.ts`.
* The `/health` healthcheck endpoint already probes `LLM_BASE_URL/health`.

### 2.3 Existing Queues Module (`apps/nest/src/modules/queues/`)
* Consolidates BullMQ queues. Already registers `QUEUE_NAMES.SCORING`.
* Uses `BaseQueueProducer` abstract class which wraps payload validation using class-validator.

## 3. Detailed Architectural Design

### 3.1 Scoring Categorization (ANC-76)
Scores computed by `ScoringEngineService` will be categorized as follows:
* **`VIABLE`**: Score $\ge$ 70
* **`REVISAR`**: Score between 40 and 69 (inclusive)
* **`BAJA_PRIORIDAD`**: Score < 40
* **`EXCLUIDO`**: If the company fails any hard filters (`status` = `EXCLUDED`), it bypasses numerical scoring and falls into this category.

### 3.2 Traceability Logs (`score_logs` Table)
To support auditing and history (traceability), we will create a new entity `ScoreLog` mapped to a new table `score_logs`. Unlike `MatchingResult` (which stores only the latest state), `score_logs` will store a record of *every* evaluation run.

#### Entity Structure (`ScoreLog`)
```typescript
@Entity({ name: 'score_logs' })
export class ScoreLog {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @ManyToOne(() => Company, { onDelete: 'CASCADE', nullable: false })
  @JoinColumn({ name: 'company_id' })
  company: Company;

  @ManyToOne(() => ProcurementNotice, { onDelete: 'CASCADE', nullable: false })
  @JoinColumn({ name: 'convocatoria_id' })
  notice: ProcurementNotice;

  @Column({ name: 'total_score', type: 'decimal', precision: 5, scale: 2 })
  totalScore: number;

  @Column({ type: 'varchar', length: 20 })
  category: 'VIABLE' | 'REVISAR' | 'BAJA_PRIORIDAD' | 'EXCLUIDO';

  @Column({ type: 'jsonb' })
  breakdown: Record<string, any>; // Vector breakdown (the 4 fit components + detailed scores)

  @Column({ type: 'text', nullable: true })
  explanation: string; // Natural Language explanation generated by LLM

  @Column({ name: 'rag_evidence', type: 'jsonb', nullable: true })
  ragEvidence: Record<string, any>; // Chunks used as RAG context (placeholder for future RAG sprints)

  @Column({ name: 'filter_result', type: 'jsonb', nullable: true })
  filterResult: Record<string, any>; // Details of hard filter checks (reason, justification, etc.)

  @Column({ name: 'model_version', type: 'varchar', length: 50 })
  modelVersion: string; // Scoring engine version (e.g., '1.0.0')

  @CreateDateColumn({ name: 'created_at', type: 'timestamptz' })
  createdAt: Date;
}
```

> [!IMPORTANT]
> **Dual Entity Registration**: The `ScoreLog` entity must be registered in:
> 1. `apps/nest/src/config/typeorm.options.ts` (runtime config)
> 2. `apps/nest/src/data-source.ts` (CLI migration config)
> A TypeORM migration must be generated via `bun run --cwd apps/nest migration:generate -- src/migrations/AddScoreLogsTable`.

### 3.3 LLM Module & Abstraction (ANC-77)

We will implement a clean provider-agnostic interface to avoid vendor lock-in.

```
                  ┌────────────────────┐
                  │   LlmProvider      │ (Interface)
                  └────────────────────┘
                            ▲
                            │ Implements
                  ┌────────────────────┐
                  │ OpenCodeGoProvider │ (Adapter Class)
                  └────────────────────┘
                            │ Calls HTTP REST
                            ▼
                  ┌────────────────────┐
                  │ Go Backend / LLM   │ (Ollama or Microservice)
                  └────────────────────┘
```

#### The `LlmProvider` Interface
Located in `apps/nest/src/modules/llm/interfaces/llm-provider.interface.ts`:
```typescript
export interface ChatMessage {
  role: 'system' | 'user' | 'assistant';
  content: string;
}

export interface ChatOptions {
  messages: ChatMessage[];
  temperature?: number;
  maxTokens?: number;
  responseFormat?: 'text' | 'json';
  jsonSchema?: object;
}

export interface ChatResponse {
  content: string;
  usage?: {
    promptTokens: number;
    completionTokens: number;
    totalTokens: number;
  };
}

export interface LlmProvider {
  chat(options: ChatOptions): Promise<ChatResponse>;
  embed(texts: string[]): Promise<number[][]>;
  health(): Promise<boolean>;
}
```

#### OpenCodeGoProvider Adapter
Located in `apps/nest/src/modules/llm/providers/opencode-go.provider.ts`:
* Injects `@nestjs/axios` `HttpService` to make REST requests.
* Uses `ConfigService` to load `LLM_BASE_URL` and `LLM_API_KEY`.
* Adds `Authorization: Bearer ${apiKey}` headers to outbound calls.
* Maps requests to OpenAI-compatible endpoints:
  * Chat: `POST /v1/chat/completions`
  * Embeddings: `POST /v1/embeddings`
  * Health check: `GET /health` (probes standard health endpoint)

#### Resilient Degradation
If LLM calls fail during scoring (network timeouts, rate limits, server down), `ScoringService` must catch the exception, log a warning, and fallback to `null` or the basic rule-based `justification` for the `explanation` field. **Scoring calculations must never block on LLM failures.**

### 3.4 BullMQ Orchestration

We will introduce a new job type to the existing `scoring` queue:

1. **`scoring-dispatch` (Existing)**: Matches a single notice ID against all companies.
2. **`company-batch-scoring` (New)**: Matches a single company ID against a list/batch of notices.

```
┌──────────────────────────────────────────────┐
│                  SCORING QUEUE               │
└──────────────────────────────────────────────┘
       │                                 │
       ▼                                 ▼
┌───────────────┐                 ┌───────────────┐
│Job: dispatch  │                 │Job: co-batch  │
│Notice -> All  │                 │Co -> Notices  │
└───────────────┘                 └───────────────┘
```

#### New Producer: `CompanyScoringBatchProducer`
* Enqueues `CompanyScoringBatchJobData` (validating `companyId` and `noticeIds` array).
* Registered in `QueuesModule`.

#### Worker Update: `ScoringWorker`
* Inspects `job.name`.
* Routes `scoring-dispatch` to the existing matching logic.
* Routes `company-batch-scoring` to a new batch service method that scores the specified notices for that company and writes both `MatchingResult` (upserted) and `ScoreLog` (appended) records.

## 4. Endpoint Mapping

### 4.1 GET `/api/scoring/:companyId/:convId`
* **Route**: `/api/scoring/:companyId/:convId`
* **Guards**: `@UseGuards(JwtAuthGuard)`
* **Description**: Returns the latest scoring result and explanation history for a company and convocatoria.
* **Response Payload (`200 OK`)**:
  ```json
  {
    "companyId": "uuid",
    "noticeId": "uuid",
    "status": "PASSED",
    "score": 85.50,
    "category": "VIABLE",
    "breakdown": {
      "technicalFit": { "score": 35.0, "details": { ... } },
      "economicFit": { "score": 20.0, "details": { ... } },
      "experienceMatch": { "score": 15.0, "details": { ... } },
      "affinityGeographical": { "score": 15.5, "details": { ... } }
    },
    "justification": "Puntaje total de afinidad: 85.5/100...",
    "explanation": "La empresa Passed Company cumple excepcionalmente...",
    "evaluatedAt": "2026-05-25T20:00:00Z"
  }
  ```

### 4.2 POST `/api/scoring/:companyId/batch`
* **Route**: `/api/scoring/:companyId/batch`
* **Guards**: `@UseGuards(JwtAuthGuard)`
* **Request DTO (`ScoringBatchDto`)**:
  ```json
  {
    "noticeIds": ["notice-uuid-1", "notice-uuid-2"]
  }
  ```
* **Description**: Enqueues a batch scoring request for the company against the specified notices into the BullMQ `scoring` queue.
* **Response Payload (`202 Accepted`)**:
  ```json
  {
    "jobId": "bullmq-job-uuid"
  }
  ```

## 5. Testing & Verification Strategy

Following the **strict TDD backend convention** in the codebase:
1. **Unit tests** for `LlmProvider` and `OpenCodeGoProvider` using mocked `HttpService`.
2. **Unit tests** for `ScoringService` and `ScoringController` showing input validation and correct service routing.
3. **Integration tests** for `ScoringWorker` verifying that `company-batch-scoring` jobs successfully persist both `MatchingResult` and `ScoreLog` entities.
4. **Mocking**: LLM calls will be stubbed using standard mock interfaces to ensure tests run offline without hitting real Ollama/Go services.
